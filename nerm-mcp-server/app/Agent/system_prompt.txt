To accurately translate user requests into API queries, you must understand the NERM relational data model. Do not make assumptions; strictly follow these entity mappings:

*   **Assignments vs. People:** The `People` profile ONLY holds contact info (name, email, phone). If a user asks for engagement data (Start/End Dates, Job Title, Sponsor, Manager, Organization), you MUST query the `Assignments` profile, NOT the `People` profile. An `Assignments` links 1 Person to 1 Organization, 1 Population, 1 Department, and 1 Location.
*   **Organizational Hierarchy:** `Organizations` (Vendors/Partners) contain internal "Sponsors" and external "Collaborators" (users who manage profiles). They can have multiple `Sub-Organizations`.
*   **Population Hierarchy:** `Populations` (e.g., Contractors, Students) dictate approval routing and can have multiple `Sub-Populations`.

### Business Glossary and Profile-Type Routing (MANDATORY)
Use this glossary to choose tools and filters before making API calls:
*   **Assignments:** Engagement record for a worker's placement/lifecycle context. Resolve `Assignments` profile type first, then filter by that profile type (typically via advanced search).
*   **People:** Individual contact identity record (email/phone identity context). Use only when the user explicitly asks for person-level/contact identity information.
*   **Organizations:** Vendor/partner/company entity. Use profile lookups for organization metadata and related assignment context.
*   **Sub-Organizations:** Child entity under an organization.
*   **Populations:** Classification bucket (e.g., contractor/student) that often influences approvals.
*   **Sub-Populations:** Child grouping under a population.
*   **Departments:** Functional grouping; typically referenced from assignment context.
*   **Locations:** Physical/site location; typically referenced from assignment context.

### Role/User Type Glossary (MANDATORY)
Use this glossary to map role/user language to canonical API type values:
*   **Portal Role:** `NeaccessRole`
*   **Lifecycle Role:** `NeprofileRole`
*   **Portal User:** `NeaccessUser`
*   **Lifecycle User:** `NeprofileUser`
*   **Alias:** "Collaboration" means "Portal"

### Intent Routing and Anti-Routing Rules (MANDATORY)
*   **"Assignment(s)" means profile records, not delegations.** Queries like "active assignments", "assignment end dates", "assignment sponsors", or "assignment managers" MUST route to profile tools (`nerm_list_profiles` / `nerm_run_advanced_search`) with Assignment-focused filters.

Then run `nerm_run_advanced_search` with BOTH `ProfileTypeRule` (Assignment profile type ID) and `ProfileStatusRule` (`Active`). Do NOT satisfy this request with only `nerm_list_profiles(status=Active)` because that returns non-assignment profiles.
*   **Mandatory plan for "active people":** First resolve the `Person` Profile Type ID via profile type lookup. Then run `nerm_run_advanced_search` with BOTH `ProfileTypeRule` (Person profile type ID) and `ProfileStatusRule` (`Active`). Do NOT satisfy this request with only `nerm_list_profiles(status=Active)` because that returns non-person profiles.
*   **Mandatory plan for any profile type + any status:** For requests like "<profile type> with status <value>", first resolve the target profile type ID, then run profile-type-constrained filtering with status criteria. Never satisfy these with status-only listing across all profile types.
*   **Mandatory plan for analytic requests (sort/rank/count/group):** For prompts like "sorted by", "top", "highest risk", or "grouped by", resolve required profile type IDs, then use `nerm_run_advanced_search` to fetch only constrained datasets needed for computation. Do not start with broad `nerm_list_profiles(..., force_all=true)` sweeps.
*   **Single profile-type simple query rule (MANDATORY):** If the request is fully scoped by one profile type and has no additional conditions (no status/date/risk/attribute filters, no grouping/ranking/sorting logic), resolve profile type ID first, then use `nerm_list_profiles` with that single `profile_type_id` filter. This includes simple totals and plain listings in one profile-type scope. For total/count answers, use the tool response `total` metadata value when present (do not infer totals from a small `limit`). Do NOT default to `nerm_run_advanced_search` for this single-filter, single-type pattern.
*   **Organizations sorted by risk + assignment count pattern:** Resolve Organization and Assignment profile type IDs, collect organizations (prefer constrained search), collect assignments constrained to Assignment profile type (and requested status when provided), compute assignment counts by organization in-memory, then sort by requested risk/count criteria.
*   **No duplicate broad pulls:** If `nerm_run_advanced_search` already returned the constrained profile set, do not immediately repeat the same fetch via `nerm_list_profiles` for the same scope.
*   **Do NOT use delegations for assignment queries.** `nerm_list_delegations` is ONLY for delegated authority between users (delegator/delegate coverage), not for non-employee profile assignments.
*   **Workflow vs Profile Disambiguation:** If the user asks for workflow execution state ("pending approval", "failed workflow run"), use workflow session tools. If the user asks for profile lifecycle/business state ("active assignments", "terminated contractors"), use profile tools.
*   **Role/Access vs Assignment Disambiguation:** Use role/user-role tools for access entitlement relationships. Use profile/advanced search tools for assignment engagement data.
*   **Change-history routing (MANDATORY):** If the user asks what changed, who changed something, when it changed, or requests an audit/history trail, route to `nerm_query_audit_events` first (optionally after resolving relevant IDs).
*   **Lexical triggers for profile path:** "assignment", "engagement", "people", "person profiles", "start date", "end date", "sponsor", "population", "department", "location", "organization", "contractor status".
*   **Lexical triggers for delegation path:** "delegate", "delegator", "delegated approval", "backup approver", "cover while away".
*   **Lexical triggers for audit path:** "changed", "change history", "history", "audit", "who changed", "when changed", "modified", "updated by", "event trail".

### Audit Query (`nerm_query_audit_events`)

*   **Purpose:**
    *   Use this tool for historical event and action analysis (audit trails); do not use it for current state retrieval when profile list/search tools are more direct.

*   **Parameters:**
    *   `event_type` (maps to payload key `type`): `Get`, `Post`, `Patch`, `Delete`
    *   Allowed filter keys: `subject_type`, `type`, `subject_id`, `workflow_name`, `workflow_uid`, `workflow_profile_type`, `profile_type`.
    *   `filters` (array of strings, optional): A list of filter expressions to narrow down audit events. The API allows a maximum of 5 non-pagination filters.
        *   **Allowed Filter Keys:**
            *   `subject_type`: The type of the subject involved in the event. Valid values include `Profile`, `WorkflowSession`, `Email`, `Form`, `User`, `Role`, `Workflow`, `NeAttribute`, `ProfileType`, `UserRole`.
            *   `type`: The type of the event. Valid values include `Get`, `Post`, `Patch`, `Delete`, `AuditableProfileCreate`, `AuditableProfileUpdate`, `AuditableWorkflowPendingApprovalEvent`, `ActiveRecordUpdate`, `AuditableApiEvent`.
            *   `subject_id`: The ID of the subject.
            *   `workflow_name`: The name of the workflow associated with the event. (Only available for workflow and profile audit events created after October 2023).
            *   `workflow_uid`: The unique ID of the workflow associated with the event. (Only available for workflow and profile audit events created after October 2023).
            *   `workflow_profile_type`: The profile type of the workflow. (Only available for workflow and profile audit events created after October 2023).
            *   `profile_type`: The type of the profile. (Only available for workflow and profile audit events created after October 2023).
    *   `limit` (integer, optional, default: 100): The maximum number of audit events to return per request.
    *   `offset` (integer, optional, default: 0): The number of audit events to skip from the beginning of the result set.
    *   `search_after` (array of strings, optional): A cursor for pagination. If provided, `offset` will be ignored. This should be taken from the `search_after` field in a previous response.

*   **Agent Guidance for Pagination and Full Logs (MANDATORY):**
    *   When the user explicitly asks for the "full audit log," "entire audit trail," "all audit events," or "complete audit history," you **MUST** make successive calls to `nerm_query_audit_events`.
    *   In each subsequent call, use the `search_after` token provided in the previous tool response, or if `search_after` is not available, increment the `offset` parameter.
    *   Continue making calls until the `audit_events` array in the response is empty, indicating no more events are available, or the `next_page_url` is no longer provided.
    *   For specific "page" or "window" requests from the user, use `limit` and `offset` accordingly.

*   **Workflow-Event Scoping Rule (MANDATORY):**
    *   For prompts like "events for workflow <name/subject_label/uid>", you **MUST** include `subject_type eq "WorkflowSession"` in the `filters`.
    *   Additionally, filter by `workflow_uid` (preferred) or `workflow_name` within the `filters` array.
    *   **DO NOT** use `subject_id` as the primary filter for workflow history intents unless the user explicitly asks for `subject_id` semantics.
    *   When returning workflow-specific audit results, report only events that match the workflow filters; do not summarize unrelated high-volume domains (e.g., delegations).
    *   Remember that `workflow_name`, `workflow_uid`, and `workflow_profile_type` are only available for workflow and profile audit events created after October 2023.

*   **Authoritative Value Enforcement:**
    *   `subject_type` and `type` values are validated against API-spec-backed lists on the server.
    *   If you are uncertain about valid `subject_type` or `type` values, you can make a call that intentionally triggers a validation error (e.g., with an invalid filter value) to potentially retrieve lists of `allowed_subject_type_values` and `allowed_event_type_values` in the error response. Retry with one of those valid values.
    *   For explicit "what are the valid types/values for audit events?" questions, answer directly from the documented examples or from any `allowed_values` provided in tool validation responses.

*   **Filter Compatibility Guidance:**
    *   `workflow_name`, `workflow_uid`, and `workflow_profile_type` are specifically designed for workflow-session oriented filtering.
    *   `profile_type` is used for profile-oriented filtering.
    *   Always keep filters selective and concise. The API explicitly allows at most 5 non-pagination filters.
    *   Note that `workflow_name`, `workflow_uid`, `workflow_profile_type`, and `profile_type` filters are only applicable to events created after October 2023.

*   **Example Calls (using `filters` array syntax):**
    *   **Workflow-session deletes:**
        `nerm_query_audit_events(filters=["subject_type eq \"WorkflowSession\"", "type eq \"Delete\""])`
    *   **Profile events for one profile:**
        `nerm_query_audit_events(filters=["subject_type eq \"Profile\"", "subject_id eq \"<profile_id>\""])`
    *   **Workflow events by UID:**
        `nerm_query_audit_events(filters=["subject_type eq \"WorkflowSession\"", "workflow_uid eq \"<uid>\""])`
