# MCP Compatibility Profile v1.0

Status: Draft (adoptable baseline)  
Audience: `tool-nerm-mcp-server` (MCP server), `testAgent` (remote/orchestrator agent), `ChatClient` (UI client)  
Scope: Message compatibility and operational interoperability across tool calls, streaming, multimodal content, and logging.

---

## 1. Versioning and Conformance

- Profile ID: `mcp-compat-profile-v1.0`
- A component is **v1.0-conformant** when it meets all `MUST` requirements and does not violate any `MUST NOT`.
- Components SHOULD expose the supported profile version in runtime/config docs.
- Backward-incompatible changes require a new minor/major profile version (e.g. `v1.1` or `v2.0`).

---

## 2. Tool Error Contract

### 2.1 Required shape

Tool results MUST use MCP tool result semantics:

- `isError: false` for successful tool execution.
- `isError: true` for failed tool execution.
- `content` MUST be a list of MCP content blocks (typed entries).

### 2.2 Error payload rules

When `isError: true`:

- At least one text block MUST be present:
  - `{"type":"text","text":"<json-string>"}`
- The JSON string SHOULD include:
  - `status: "error"`
  - `error: <stable_error_code>`
  - `message: <human-readable explanation>`
- `structuredContent` MAY be present for machine parsing.

### 2.3 Success payload rules

When `isError: false`:

- At least one `content` block MUST be present.
- Text metadata SHOULD be JSON-encoded string in a text block for cross-client compatibility.
- If present, `structuredContent` MUST be JSON-serializable.

### 2.4 Prohibitions

- Components MUST NOT infer success/failure from text-only heuristics when `isError` is available.
- Components MUST NOT drop `isError`/`structuredContent` fields in pass-through layers.

## 3. Content Block Support Matrix

This matrix defines baseline handling expectations.

| Block Type | MCP Server (tool-nerm-mcp-server) | testAgent | ChatClient |
|---|---|---|---|
| `text` | MUST emit | MUST parse and preserve | MUST render |
| `image` | MUST emit for chart/image tools | MUST parse and preserve | MUST render (native) |
| `audio` | MAY emit | SHOULD preserve | SHOULD provide fallback |
| `resource`/`resource_link` | MAY emit | SHOULD preserve | SHOULD provide fallback |
| unknown type | MUST not crash | MUST preserve raw block | MUST show explicit unsupported-block fallback |

### 3.1 Unknown block handling

- Unknown block types MUST NOT cause request failure.
- Unknown blocks SHOULD be passed through unchanged where possible.
- UI MUST present a safe fallback message and optionally raw inspector.

## 4. Stream Framing and Retry Semantics

### 4.1 SSE framing

- Consumers MUST parse SSE by event frame, not single-line parsing.
- Multi-line `data:` frames MUST be joined per SSE spec.
- If `event:` and `id:` are present, consumers SHOULD preserve/use them.

### 4.2 Ordering and deduplication

- Consumers SHOULD support idempotency/dedup safeguards for replayed events.
- Consumers SHOULD preserve arrival order within a stream unless explicit sequence keys are provided.

### 4.3 Retry behavior

- On transient transport failures, clients SHOULD retry with bounded backoff.
- Retry policy SHOULD be documented (attempts, backoff window, timeout).
- If retry is exhausted, client MUST surface explicit transport error state.

### 4.4 Session behavior (streamable-http)

- Clients MUST follow server session requirements (if stateful mode enabled).
- Session mismatch/expiry errors SHOULD trigger re-init flow before hard-fail.

## 5. Multimodal Fallback Policy

### 5.1 Primary policy

- For images/charts, producers SHOULD emit native MCP `image` blocks with base64 `data`.
- Consumers SHOULD prefer native block rendering over markdown reconstruction.

### 5.2 Fallback policy

- Markdown data URL fallback MAY be included only when explicitly requested or required by downstream client capability.
- Fallback payloads MUST be clearly identified in metadata (e.g., `markdown` field).
- Producers MUST avoid duplicate large payload representations unless fallback is required.

### 5.3 Size controls

- Producers SHOULD apply adaptive size controls (downsampling/DPI) for large media.
- Producers SHOULD include size metadata (`png_bytes`, target size, warnings).
- Media oversize SHOULD degrade gracefully (warning + best-effort output), not crash tool calls.

---

## 6. Logging and Redaction Expectations

### 6.1 Required logging events

At minimum, tool invocation logs SHOULD include:

- `tool_call_input tool=<name> args=<serialized-sanitized>`
- `tool_call_output tool=<name> output=<serialized-sanitized>`

### 6.2 Redaction/sanitization

- Sensitive keys (authorization/token/password/api_key/secret) MUST be redacted.
- Binary payloads MUST NOT be logged raw.
- For image blocks, base64 image payload SHOULD be logged as:
  - `<base64_image len=<n>>`
- Log payloads SHOULD be truncated to configured max bytes.

### 6.3 Stability requirements

- Logging logic MUST be JSON-serialization-safe for custom/typed objects.
- Logging failures MUST NOT break tool execution.

## 7. Minimal Interoperability Examples

### 7.1 Success result (text + image)

```json
{
  "content": [
    {
      "type": "text",
      "text": "{\"status\":\"success\",\"chart_type\":\"pie\",\"png_bytes\":39285}"
    },
    {
      "type": "image",
      "mimeType": "image/png",
      "data": "<base64_png_bytes>"
    }
  ],
  "isError": false
}
```

### 7.2 Error result

```json
{
  "content": [
    {
      "type": "text",
      "text": "{\"status\":\"error\",\"error\":\"invalid_chart_spec\",\"message\":\"No plottable numeric series found.\"}"
    }
  ],
  "isError": true
}
```

## 8. Adoption Checklist (per component)

### MCP Server (`tool-nerm-mcp-server`)

- [ ] Tool results follow `isError` contract consistently.
- [ ] Multimodal output uses typed MCP blocks.
- [ ] Logging redaction and image-length masking enabled.

### Orchestrator (`testAgent`)

- [ ] Preserves `isError` and `structuredContent`.
- [ ] Parses typed content blocks without dropping unknown types.
- [ ] Stream parser is SSE-frame compliant.

### UI (`ChatClient`)

- [ ] Renders `text` and `image` native blocks.
- [ ] Provides explicit fallback for unsupported block types.
- [ ] Handles stream ordering/replay safely.
